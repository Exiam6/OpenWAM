## 0. 为什么是这一步

[EXPERIMENT_PLAN](EXPERIMENT_PLAN.md) §1 的事实：66 条演示、4000 步训出的三个臂闭环只有 5/42、5/42、3/42，两个任务全零，架构差异测不出来。§4 曾把"扩大数据规模"搁置到官方基线之后；官方基线已在 Torch 跑出 58/60（[records/official-baseline-20261002-result.json](records/official-baseline-20261002-result.json)），说明基准可做。而 [CROSS_CLUSTER_REPRODUCIBILITY](CROSS_CLUSTER_REPRODUCIBILITY.md) §5 又证明：这台 Blackwell 机器只能跑 OIDN 2.3.3，官方 checkpoint 在它上面必然处于训练分布之外（10/59）。

所以在这台机器上唯一干净的做法是：**演示数据和闭环评测用同一个渲染器**。我们自己采的数据正是这样（采集和评测都在 gpu-02、都用 2.3.3）。扩到约 11 倍数据后，三个臂的比较是同机、同渲染器、同配方的受控比较。

## 3. 预注册

读数前写下：

1. **数据规模**：`adjust_bottle` 三个臂的 screen 成功率应明显高于旧研究的 5/15（每臂 15 个 cell）。`handover_block` 和 `place_object_basket` 是否离开零是本研究**最重要的未知量**——若仍为零，说明问题不在数据量，而在配方/模型规模，之后的架构比较都要换任务。
2. **RAE 的受控比较**：`raw768_native`（768 维 DINOv3 潜变量直接扩散，即 RAE 的核心主张）对 `svae48_native`（压缩到 48 维）。RAE 的主张预测 raw768 ≥ svae48。旧研究 5/42 对 3/42 是噪声水平。
3. **宽头**：`raw768_wide` 对 `raw768_native`。旧研究 5 对 5。**不预测方向**；判定规则：把 3 个种子 × 全部有效场景的配对 cell 合并，只有 wide-only 与 base-only 的计数差在符号检验下 p < 0.05 才算有差别。
4. **对官方 checkpoint 的参考**：若任一臂在 extended 集上超过官方的 10/59（同机同渲染器），就是"渲染器内分布训练胜过 30 倍步数、2.5 倍深度但渲染器外分布的官方模型"的直接证据，进一步支持 §5 的上游结论。

辅助指标（dev flow loss）照旧记录，**不用于任何选择或声称**（旧研究已证明它不跟踪终点）。

## 4. 执行方式

每张卡一个守护进程 `orchestrate.py --gpu N`（已部署、待启动），逻辑：

- "空闲"的严格定义：无 compute 进程且显存 < 100 MiB，**连续 10 次（10 分钟）轮询都满足**才启动阶段——同事的作业是不断重生的短 worker，瞬时空闲不算释放。
- 两个守护进程通过 `claims/` 目录共享工作队列（采集按 episode、训练按 run、评测按 cell 原子认领）；任一张卡单独也能把整个研究跑完，只是慢一倍。
- 阶段顺序 collect → prepare → pipeline → evaluate，每个阶段由 `launch.py` 在启动瞬间再查一次卡、锁 `gpu-N.lock`、冻结环境（与 10-01 研究逐项相同，只换卡）。
- 崩溃的 episode / run 自动回收（run 从 2000 步一存的 resume 继续）；失败的 run 不重试（`automatic_retries: false`）。
- 绝对截止 5 天；暂停文件 `paused.json` 随时能停。
